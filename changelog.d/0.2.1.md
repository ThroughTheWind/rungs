# 0.2.1 — pending

The number is provisional. It is decided from these fragments at cut time, not from this heading —
if a feature lands before the cut, this becomes a minor and the file is renamed.

## Added

- **The concurrency loop exists.** `rungs session start <branch>`, `rungs preflight`,
  `rungs land <branch>` and `rungs worktrees` — the four commands the `concurrency` module had
  documented for weeks without any of them existing (WI-062, closes F-026). They obey
  [ADR-0009](../docs/decisions/ADR-0009-rungs-drives-git.md), which is the first decision letting
  rungs drive git at all: **verify before you advance** (`land` merges onto a scratch ref, gates
  *that* tree, then moves the branch with a compare-and-swap, so a refusal leaves the integration
  branch bit-for-bit unchanged), **never destroy — only refuse** (nothing deletes a branch, a
  worktree or a commit; a refused land parks its merge rather than discarding it), and **never hold
  the integration branch**. `session start` states it when it falls back to an unverified tip;
  `worktrees` reports and removes nothing, and flags the row that matters — merged *and* dirty.
- `module-commands-exist`: every command a module tells a repo to run must be one the CLI
  dispatches. Both sides are derived from the `switch` in `src/cli.ts`, so the gate cannot drift the
  way the hand-kept documentation it checks did.

## Fixed

- `rungs setup <path>` wrote git config into the **current directory** while reporting success
  about the repository you named. The path is the argument *after* the subcommand, so omitting
  `git` put it in the subcommand slot, where it was discarded — and the subcommand was never
  validated, so `rungs setup banana` also exited 0 and did the same thing. `setup` now refuses
  anything but `git` and names the correct form, as `backlog` has always done for `archive`
  (closes F-027).
- `--set` refused a malformed key but not an unknown one, then printed `set nosuch.param = 1` as
  though it had applied — so a mistyped parameter installed the default and reported that it had
  not. Both names are now checked: an unknown module lists the fifteen, and an unknown parameter
  lists what that module actually takes (closes F-028).

- `release-version-consistent` takes an `exclude` list, so a package that is deliberately versioned
  on its own no longer reads as a disagreement. Empty by default: which packages share a version is
  a judgement about your repo, and an engine guessing it is how a healthy layout gets a red gate.
  `all-agree` is unchanged, so the gate still needs no opinion about which file is right
  (closes F-023).
- The same gate's finding named each disagreeing file beside the version it states
  (`package.json=1.2.0, web/package.json=1.1.0`) instead of telling you to run
  `rungs release sync-version` — **a command that does not exist and never has**. The `autofix`
  hint is now printed only when one is actually declared (closes F-024).
- Self-test fixtures for `computed-claim` execute rather than reporting *unrun*, including one
  asserting that excluding one sibling does not blind the gate to a different one. An `exclude`
  that silently widened would be worse than no gate, because it would still report green.

## Changed

- rungs' own docs site is versioned in lockstep with the CLI. It had reached `0.2.0` while
  `site/package.json` sat at `0.0.1`, and aligning it — rather than excluding it — means the gate
  checks two manifests instead of being told to look away. `modules/release` 1.1.0 → 1.2.0.
- `modules/concurrency` 1.0.0 → 1.1.0. Its "a failure is attributed" section is now marked as
  **design, not behaviour** — `land` blocks on any red gate in the merged tree, and the
  inherited/INTRODUCED split is not built. Saying so is the correction; describing it as shipped is
  what the same document did wrong about four commands.
